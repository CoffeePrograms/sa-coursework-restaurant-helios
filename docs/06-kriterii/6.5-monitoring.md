# 6.5. Мониторинг

## US-15. Просмотр логов {#us-15}

**Как администратор, я хочу просматривать логи запросов к системе, чтобы находить причины ошибок.**

Связь: [БП-06](../01-biznes-trebovaniya/1.5-biznes-processy.md#bp-06) «Мониторинг и сопровождение системы».

Сервисы: BFF, Administration.

Статус: спринт 2, реализовано.

Критерии приемки приведены в [таблице 6.11](#tablitsa-6-11).

Таблица 6.11 — Критерии приемки [US-15](#us-15)
{: #tablitsa-6-11 .caption }

| Критерий | Сценарий |
| --- | --- |
| <span id="us-15-ac-1"></span>AC-1. Запись лога | Допустим BFF выполнил HTTP-запрос<br>Когда запрос завершен<br>Тогда BFF пишет запись журнала с полями по [НФТ-05](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-05) и передает ее в Administration через RabbitMQ<br>И Administration сохраняет запись в ClickHouse<br>Основание: [НФТ-05](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-05) «Журнал запросов» |
| <span id="us-15-ac-2"></span>AC-2. Просмотр логов за период | Допустим администратор открыл дашборд «Логи» в Grafana<br>Когда он задает период<br>Тогда он видит записи журнала за этот период<br>Основание: [НФТ-06](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-06) «Срок хранения журнала»<br>Основание: [НФТ-07](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-07) «Мониторинг» |
| <span id="us-15-ac-3"></span>AC-3. Administration недоступен | Допустим сервис Administration временно не работает<br>Когда BFF передает записи журнала<br>Тогда записи остаются в очереди RabbitMQ и сохраняются после восстановления сервиса<br>Основание: [НФТ-05](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-05) «Журнал запросов» |

## US-16. Метрики и дашборды {#us-16}

**Как администратор, я хочу видеть метрики системы на дашбордах, чтобы замечать рост времени ответа и ошибок и решать, что оптимизировать.**

Связь: [БП-06](../01-biznes-trebovaniya/1.5-biznes-processy.md#bp-06) «Мониторинг и сопровождение системы».

Сервисы: Administration.

Статус: спринт 3, частично: Prometheus и Grafana развернуты, дашборды строятся по логам и метрикам ClickHouse; метрики сервисов не собираются ([AC-1](#us-16-ac-1), [AC-2](#us-16-ac-2)), см. [раздел 7.2](../07-rezultat/7.2-naydeno-pri-revizii.md).

Критерии приемки приведены в [таблице 6.12](#tablitsa-6-12).

Таблица 6.12 — Критерии приемки [US-16](#us-16)
{: #tablitsa-6-12 .caption }

| Критерий | Сценарий |
| --- | --- |
| <span id="us-16-ac-1"></span>AC-1. Сбор метрик | Допустим сервисы системы работают<br>Когда Prometheus опрашивает сервисы<br>Тогда он сохраняет время ответа и долю ошибок по каждому сервису<br>Основание: [НФТ-07](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-07) «Мониторинг» |
| <span id="us-16-ac-2"></span>AC-2. Дашборд | Допустим метрики собраны<br>Когда администратор открывает дашборд в Grafana и выбирает период<br>Тогда он видит время ответа и долю ошибок по сервисам за этот период<br>Основание: [НФТ-07](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-07) «Мониторинг» |
| <span id="us-16-ac-3"></span>AC-3. Сервис не отвечает | Допустим один из сервисов перестал отвечать<br>Когда администратор открывает дашборд<br>Тогда видно, что данных по этому сервису нет<br>Основание: [НФТ-07](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-07) «Мониторинг»<br>Основание: [НФТ-12](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-12) «Доступность» |
