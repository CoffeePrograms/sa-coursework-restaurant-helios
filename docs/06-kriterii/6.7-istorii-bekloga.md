# 6.7. Истории бэклога

Истории бэклога в спринты не вошли. Их критерии приемки приведены кратко в [таблице 6.14](#tablitsa-6-14): подробные сценарии пишутся, когда история берется в работу. Связи с бизнес-процессами — в [таблице 2.4](../02-trebovaniya/2.4-polzovatelskie-istorii.md#tablitsa-2-4).

Таблица 6.14 — Истории бэклога
{: #tablitsa-6-14 .caption }

| История | Критерии приемки (кратко) | Допущения и вопросы |
| --- | --- | --- |
| <span id="us-02"></span>[US-02](#us-02) «Загрузка меню из iiko»<br>Как менеджер, я хочу загружать меню на день из iiko ресторана, чтобы не переносить блюда вручную.<br>Статус: бэклог. | <span id="us-02-ac-1"></span>[AC-1](#us-02-ac-1). Успешная загрузка: блюда, которых нет в списке всех блюд, добавляются, меню на дату создается<br><span id="us-02-ac-2"></span>[AC-2](#us-02-ac-2). iiko недоступна (негатив): меню не меняется, менеджер видит ошибку и составляет меню вручную ([US-01](6.1-menyu.md#us-01))<br><span id="us-02-ac-3"></span>[AC-3](#us-02-ac-3). Меню с бронями (негатив): меню не заменяется. Основание: [ОГР-03](../02-trebovaniya/2.2-ogranicheniya-i-pravila.md#ogr-03) «Меню с бронями не меняется» | Допущение: ресторан ведет меню в iiko и дает доступ к API, формат обмена нужно согласовать. |
| <span id="us-08"></span>[US-08](#us-08) «Отправка отчета по email»<br>Как менеджер, я хочу отправлять отчет ресторану по email из системы, чтобы не пересылать файл вручную.<br>Статус: бэклог. | <span id="us-08-ac-1"></span>[AC-1](#us-08-ac-1). Отправка отчета: PDF уходит на email ресторана, менеджер видит подтверждение<br><span id="us-08-ac-2"></span>[AC-2](#us-08-ac-2). Email ресторана не указан (негатив): отчет не отправляется, система просит указать адрес<br><span id="us-08-ac-3"></span>[AC-3](#us-08-ac-3). Ошибка отправки (негатив): менеджер видит ошибку и может повторить отправку или скачать PDF | Допущение: email ресторана хранится в настройках системы. |
| <span id="us-09"></span>[US-09](#us-09) «Автоматическая отправка отчета»<br>Как менеджер, я хочу, чтобы отчет уходил ресторану автоматически в заданное время, чтобы ресторан получал заказы, даже если я не отправлю их вручную.<br>Статус: бэклог. | <span id="us-09-ac-1"></span>[AC-1](#us-09-ac-1). Отправка по расписанию: в заданное время отчет за день уходит на email ресторана без участия менеджера<br><span id="us-09-ac-2"></span>[AC-2](#us-09-ac-2). Броней нет: отчет не отправляется<br><span id="us-09-ac-3"></span>[AC-3](#us-09-ac-3). Ошибка отправки (негатив): менеджер получает уведомление и может отправить отчет вручную ([US-08](#us-08)) | Допущение: время отправки задает менеджер, оно раньше 12:00.<br>Открытый вопрос: нужно ли ресторану письмо «заказов нет» и что делать с бронями после отправки. |
| <span id="us-10"></span>[US-10](#us-10) «Передача обедов в iiko через API»<br>Как менеджер, я хочу, чтобы список обедов за день передавался в iiko ресторана через API, чтобы ресторан получал заказы в своей системе без файлов и писем.<br>Статус: бэклог. | <span id="us-10-ac-1"></span>[AC-1](#us-10-ac-1). Передача обедов: iiko получает те же данные, что и отчет ([US-06](6.3-otchety-dlya-restorana.md#us-06)), менеджер видит успешную передачу<br><span id="us-10-ac-2"></span>[AC-2](#us-10-ac-2). Ошибка API (негатив): система сообщает об ошибке, менеджер может отправить отчет по email ([US-08](#us-08)) | Допущение: ресторан работает в iiko и дает доступ к API. |
| <span id="us-11"></span>[US-11](#us-11) «Регистрация и вход через Яндекс»<br>Как сотрудник, я хочу регистрироваться и входить через аккаунт Яндекса, чтобы не заводить отдельный пароль.<br>Статус: бэклог; в интерфейсе есть только кнопка входа, обработки на сервере нет. | <span id="us-11-ac-1"></span>[AC-1](#us-11-ac-1). Первый вход: система создает учетную запись по данным Яндекса и выдает cookie сессии. Основание: [НФТ-02](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-02) «Сессия пользователя»<br><span id="us-11-ac-2"></span>[AC-2](#us-11-ac-2). Повторный вход: система выдает cookie сессии с ролями пользователя. Основание: [НФТ-02](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-02) «Сессия пользователя»<br><span id="us-11-ac-3"></span>[AC-3](#us-11-ac-3). Отказ на стороне Яндекса: учетная запись не создается, пользователь остается на странице входа<br><span id="us-11-ac-4"></span>[AC-4](#us-11-ac-4). Сессия истекла (негатив): система просит войти заново. Основание: [НФТ-02](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-02) «Сессия пользователя» | Сейчас в интерфейсе есть только кнопка входа, обработки на сервере нет.<br>Допущение: новая учетная запись создается без ролей, пользователь работает как сотрудник ([ОГР-05](../02-trebovaniya/2.2-ogranicheniya-i-pravila.md#ogr-05) «Только сотрудники компании»). |
| <span id="us-17"></span>[US-17](#us-17) «Нагрузочное тестирование»<br>Как администратор, я хочу запускать нагрузочное тестирование, чтобы проверить, выдержит ли система пиковую нагрузку.<br>Статус: бэклог. | <span id="us-17-ac-1"></span>[AC-1](#us-17-ac-1). Запуск теста: сервисы получают серию запросов, время ответа и доля ошибок видны на дашборде ([US-16](6.5-monitoring.md#us-16)). Основание: [НФТ-11](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-11) «Производительность» | Открытый вопрос: целевая нагрузка (число одновременных пользователей и допустимое время ответа) не определена. |
| <span id="us-19"></span>[US-19](#us-19) «Удаление устаревших данных»<br>Как администратор, я хочу, чтобы система сама удаляла данные об обедах старше 30 дней, чтобы не хранить лишние данные о сотрудниках.<br>Статус: бэклог. | <span id="us-19-ac-1"></span>[AC-1](#us-19-ac-1). Ежедневная очистка: обеды старше 30 дней удаляются, обеды за последние 30 дней остаются. Основание: [НФТ-15](../02-trebovaniya/2.3-nefunkcionalnye-trebovaniya.md#nft-15) «Персональные данные»<br><span id="us-19-ac-2"></span>[AC-2](#us-19-ac-2). Отчет за удаленный день (негатив): система сообщает, что данных за этот день нет | Допущение: удаляются только обеды; блюда, меню и схема зала остаются. Срок 30 дней лучше вынести в настройку. |
