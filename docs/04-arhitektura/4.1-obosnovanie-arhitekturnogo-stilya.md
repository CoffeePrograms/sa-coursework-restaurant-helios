# 4.1. Обоснование архитектурного стиля

Рассматривались три стиля: монолит, модульный монолит и микросервисы. Сравнение по критериям приведено в [таблице 4.1](#tablitsa-4-1).

Таблица 4.1 — Сравнение архитектурных стилей
{: #tablitsa-4-1 .caption }

| Критерий | Монолит | Модульный монолит | Микросервисы |
| --- | --- | --- | --- |
| Время до первой версии | Короткое | Короткое | Дольше: контракты gRPC, брокер, сборка каждого сервиса |
| Параллельная работа четырех разработчиков | Общий код, частые конфликты | Границы модулей в одном решении | Отдельные сервисы, базы, сборка и тесты |
| Разные модели хранения | Одна база | Одна база или несколько в одном процессе | У сервиса своя база: брони в PostgreSQL, схема зала документом в MongoDB, журнал в ClickHouse |
| Изоляция отказов | Сбой останавливает всю систему | Сбой останавливает всю систему | Отказ Administration не мешает бронированию, записи журнала ждут в очереди |
| Правила на стыке данных | Одна транзакция | Одна транзакция | Нужны вызовы между сервисами: занятость места, меню на сегодня, удаление с бронями |
| Масштабирование | Целиком | Целиком | По сервисам |
| Стоимость эксплуатации | Один процесс и одна база | Один процесс и одна база | Шесть сервисов, четыре базы, брокер, мониторинг, Kubernetes |

Выбраны микросервисы. Решающими были три критерия: разные модели хранения данных, изоляция отказов вспомогательных частей (журнал и мониторинг не должны останавливать бронирование) и параллельная работа четырех разработчиков с отдельной сборкой и тестами по сервисам.

Цена выбора — сложность и согласованность данных. Правила, которые затрагивают несколько сервисов, требуют вызовов между ними, и в текущей версии часть из них проверяет только интерфейс ([раздел 7.2](../07-rezultat/7.2-naydeno-pri-revizii.md)). Эксплуатация дороже, первая версия заняла больше времени.

Для продакшена при нагрузке одного офиса я выбрала бы модульный монолит: Menu, Lunch, Hall и Authorization — модули одного приложения с общей базой PostgreSQL, где правила [ОГР-04](../02-trebovaniya/2.2-ogranicheniya-i-pravila.md#ogr-04) и [ОГР-09](../02-trebovaniya/2.2-ogranicheniya-i-pravila.md#ogr-09) проверяются в одной транзакции. Журнал и мониторинг остаются отдельными, как сейчас. Выделять сервисы стоит, когда появятся интеграции с iiko и почтой или несколько офисов с разной нагрузкой.

Сервисы приведены в [таблице 4.2](#tablitsa-4-2). BFF — единая точка входа для одного клиента, веб-приложения на React. Он вызывает Menu, Lunch и Hall по gRPC, Authorization — по HTTP, и передает логи в Administration через RabbitMQ.

Таблица 4.2 — Сервисы системы
{: #tablitsa-4-2 .caption }

| Сервис | Назначение | Хранилище |
| --- | --- | --- |
| BFF (TavernHelios.Server) | Принимает запросы веб-приложения, собирает данные под экраны (схема зала с бронями, отчет в PDF и Excel), рассылает обновления броней через SignalR, проверяет вход, передает логи | — |
| Authorization (TavernHelios.Auth) | Регистрация и вход по логину и паролю, пользователи, роли администратора и менеджера | PostgreSQL, EF Core |
| Menu (MenuService) | Блюда, меню, расписание меню по датам | MongoDB |
| Lunch (ReservationService) | Обеды: блюда, время, стол и место | PostgreSQL, EF Core |
| Hall (LayoutService) | Схема зала: столы и места | MongoDB |
| Administration (AdministrationService) | Прием логов из RabbitMQ и запись в ClickHouse | ClickHouse, Dapper |
